# 2.13 — Interview Questions: Global State Management

> Maps to [2.13.a](./2.13.a-Context-API-App-Wide-State.md)–[2.13.e](./2.13.e-Avoiding-Overengineered-State-Logic.md)

[<< 2.13 Overview](./README.md)

---

## Beginner — Q1

### What is the React Context API for?

**Model answer:** Providing values from ancestors to descendants without threading props through every level—theme, auth session UI, router-like dependencies.

---

## Beginner — Q2

### Why does a new context object each render cause updates?

**Model answer:** React compares context values by reference; a new object identity means ‘value changed,’ so all consumers re-render.

---

## Intermediate — Q3

### When is Zustand preferable to Context?

**Model answer:** When many components need shared mutable client state with selective subscriptions and you want less Provider boilerplate than a large context split—but you still enforce conventions.

---

## Intermediate — Q4

### When should state stay local?

**Model answer:** When only one subtree needs it, or lifting one level suffices—default to colocation until sharing is proven.

---

## Advanced — Q5

### How do you avoid context re-render storms?

**Model answer:** Split contexts by update frequency, memoize stable value objects, keep consumers small, and consider stores with fine-grained subscriptions for hot paths.

---

## Advanced — Q6

### What is overengineered state logic?

**Model answer:** Abstractions that exceed team comprehension or problem complexity—extra stores, sync effects, and patterns that slow delivery without measurable wins.

---

## Quick-fire

| # | Q | A |
|---|--|--|
| 1 | createContext | makes a context object |
| 2 | Provider | supplies value to subtree |
| 3 | useContext | reads nearest Provider value |
| 4 | Zustand selector | subscribe to slice of store |
| 5 | URL state | shareable/bookmarkable filters |
| 6 | Global smell | state only one file used |
