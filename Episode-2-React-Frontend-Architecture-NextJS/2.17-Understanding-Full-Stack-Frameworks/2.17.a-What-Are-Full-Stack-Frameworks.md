# 2.17.a — What Are Full Stack Frameworks?

> **In one sentence:** They unify server and browser concerns in one application system—routing, rendering, and server logic colocated with UI—so teams ship vertical slices faster while still owning security and ops discipline.

**Navigation:** [← 2.17 Overview](./README.md) · [Next → 2026 Landscape](./2.17.b-Modern-Web-Frameworks-Landscape-2026.md)

---


## 1. Defining “full stack framework” without hype

A **full stack framework** (in the modern web sense) is a productized **application platform** that:

1. **Owns the HTTP boundary** — routing, request handling, sometimes middleware/edge.
2. **Coordinates rendering** — server HTML/RSC, client hydration, streaming.
3. **Embeds server capabilities** — mutations via actions, Route Handlers, or loader/action patterns.
4. **Ships as one codebase** — shared modules for validation, types, auth helpers.

It is **not** automatically “a database inside React.” Persistence is still usually **external** (Postgres, MongoDB, SaaS APIs).

### 1.1 “Single system” — what actually becomes one?

| Layer | Often unified in one repo/deploy |
| ----- | -------------------------------- |
| UI routes + server routes | Yes |
| Build + typecheck | Yes |
| Auth session between UI and server handlers | Often easier |
| Database schema | Sometimes separate service owned by platform team |

**Single system** usually means **one deployable application boundary** and **one mental model** for how requests flow—not that every concern collapses into one process forever.

### 1.2 Problems these frameworks optimize

| Pain in “SPA + separate API” | Full stack framework angle |
| ---------------------------- | -------------------------- |
| Duplicate DTO validation | Shared Zod/schemas |
| CORS + cookie complexity | Same-origin server routes |
| SSR glue custom per company | Conventions + docs |
| Two deploy pipelines to coordinate | One pipeline (still can be complex) |

### 1.3 Costs you must still pay

- **Security:** server code is privileged; any exposed endpoint is attack surface.
- **Complexity:** caching, partial rendering, and deployment cold starts become *your* literacy topics.
- **Lock-in (soft):** platform-specific APIs creep in unless you wrap them.

### 1.4 Interview-grade definition

“A full stack web framework gives me **first-class server execution** next to my UI with **shared modules and routing conventions**, so I ship features as **vertical slices** instead of constantly stitching a SPA to a separate REST service.”

### 1.5 Comparison to “API + web portal” two-repo pattern

Two-repo is still valid at scale with **platform boundaries**. Frameworks shine when **product velocity** and **small team ownership** dominate and cross-repo friction hurts more than modular isolation helps.

### 1.6 Ownership model

Define **who reviews** server mutations vs UI. Some teams use CODEOWNERS on `app/api`, `server`, or service folders—even inside one repo.

## Part 2 — Deep Encyclopedia (What Are Full Stack Frameworks?)

> **How to use:** Each drill = **scenario** → **prompt** → **model answer** → optional **code sketch**.

### E001 — Drill 1: Backend engineer fears 'frontend framework' owns their APIs.

**Scenario:** Backend engineer fears 'frontend framework' owns their APIs. (variation 1: assume 2026 maintenance expectations—security patches, LTS Node, and supply-chain scanning in CI.)

**Prompt:** What architectural decision do you document, and what measurable outcome validates it for case #1?

**Model answer:** I separate **product goals** (time-to-market, SEO, offline, compliance) from **organizational constraints** (skills, existing services, cloud contracts). I propose the smallest **vertical slice** through the stack (UI → server → persistence) and measure **lead time**, **defect rate**, and **p95 latency** for that slice. For drill #1, I call out risks (coupling, vendor APIs, unclear ownership) and mitigations (module boundaries, ADRs, hexagonal ports on the server). I avoid treating any framework as magic—it still needs engineering discipline.

```txt
Single deployable artifact
├── UI routes / components
├── Server handlers / actions
├── Shared validation + types
└── External services (DB, queue, payments)
```
